# 通信节拍：为什么使用 250 Hz 和 3 ms 接收预算

在 2026-10-27 的被动通信测试中，SDK 一次完整交换的耗时中位数约为 2.63 ms。原来的 1 ms 接收窗口经常等不到新反馈，而 4 ms 周期加 3 ms 接收预算在各组短时测试中都能收齐反馈。因此，当前 ROS 配置采用 **每臂 250 Hz、接收预算 3 ms**。

测试使用本项目的主机、两臂 MCU 和两块 `ax88179_178a` USB 网卡。以太网均为 100 Mbps 全双工，USB 侧速率为 5000 Mbps，测试时网卡电源状态为 active。测试没有记录 MCU 和电机固件的版本。

## 1. 周期与接收预算

| 参数 | 原配置 | 当前配置 | 位置 |
| --- | --- | --- | --- |
| 主机控制周期 `period` | 0.002 s，500 Hz | 0.004 s，250 Hz | [control.yaml](z1_bringup/config/control.yaml) |
| UDP 接收预算 `receive_budget_us` | 1000 μs | 3000 μs | [communication.yaml](z1_bringup/config/communication.yaml) |

每臂都有独立的控制线程，在线程内依次执行：

```text
发送上一轮输出 → 接收 MCU 反馈 → 计算下一轮输出 → 等待下一个控制时隙
```

报文到达后，接收会立即返回；3 ms 是接收代码设置的等待预算，实际返回时间还会受到系统调度影响。接收和计算共用一个周期，所以节点启动时要求：

```text
receive_budget_us × 10⁻⁶ < period
```

当前配置在接收预算之外留出约 1 ms，供发送、控制计算和调度使用。线程按照绝对时间网格运行，错过的时隙会被跳过并计数。

其他时间参数属于不同环节：`publish_rate=100 Hz` 控制 ROS 状态发布，`feedback_timeout=80 ms` 控制反馈有效期。标定工具使用独立的节拍，每次被动交换后等待 10 ms，接收预算为 5 ms。MCU 的内部控频由固件决定。

## 2. SDK 接收窗口对照

每种条件、每臂各交换 500 次。耗时包含接收超时的调用，单位是 ms：

| 机械臂 | 周期 / 接收预算 | 取得新有效反馈 | 最长连续未取得 | 交换耗时中位数 / 最大值 |
| --- | --- | --- | --- | --- |
| 左 | 2 ms / 1 ms | 268 / 500 | 5 次 | 1.199 / 1.411 |
| 右 | 2 ms / 1 ms | 269 / 500 | 5 次 | 1.210 / 1.384 |
| 左 | 4 ms / 3 ms | 500 / 500 | 0 次 | 2.632 / 2.829 |
| 右 | 4 ms / 3 ms | 500 / 500 | 0 次 | 2.639 / 2.728 |

更早的一轮测试中，2 ms / 1 ms 配置下左、右臂分别取得 263 / 500 和 270 / 500 次新反馈，4 ms / 3 ms 下则都是 500 / 500。两轮结果一致地表现为：原来的接收窗口偏短，延长窗口后新反馈的获取更完整。

“取得新反馈”是按本轮接收窗口来计数的。晚到的回复可能被下一轮的旧队列清理丢弃，因此窗口内的缺帧数与链路丢包数含义不同。这组对照同时改变了周期和接收预算，两个因素的独立影响还没有分离。

## 3. 内核时间戳：往返约 2.4 ms

原始 UDP 测速程序会发送发现请求和 140 字节的全零被动帧，使用 Linux `SO_TIMESTAMPING` 的软件发送、接收时间戳。程序先经过回环模拟器检查；在逐次请求测试中，每次收到回复后才发送下一个请求，以减少配对歧义。它不经过 ROS、运动学、动力学或 SDK 解码。

单臂 250 Hz、每臂 1000 次的结果如下。时间单位是 ms，除 P99 外都是中位数：

| 测量环节 | 左臂 | 右臂 |
| --- | --- | --- |
| 应用发送调用前 → 内核发送时间戳 | 0.0301 | 0.0208 |
| 内核发送 → 内核接收 | 2.4351 | 2.4328 |
| 内核接收 → 应用读到报文 | 0.0693 | 0.1152 |
| 应用一次完整交换 | 2.5353 | 2.5696 |
| 内核发送 → 接收的 P99 | 2.4522 | 2.4484 |
| 收到 / 发送 | 1000 / 1000 | 1000 / 1000 |

各项分别取分位数，因此分项中位数相加不会严格等于总耗时中位数。100 Hz 测试中，两臂的内核往返中位数也约为 2.434 ms。

两臂同时以 250 Hz 运行时，各完成 2000 / 2000 次收发，测试程序没有跳过发送时隙；内核往返中位数分别为 2.4334 ms 和 2.3436 ms。

在同链路、140 字节 ICMP payload 的 ping 对照中，两臂各 20 次全部收到回复，平均往返分别为 0.237 ms 和 0.265 ms。

**测量结果**：大部分交换时间位于内核发送与接收的时间戳之间。这一段包含驱动、USB 网卡、链路和设备处理。

**据此选择的排查方向**：优先检查机械臂的 UDP 业务处理、固件任务节拍和内部电机通信。ICMP 与控制 UDP 的处理路径不同，现有数据还没有把约 2.4 ms 分解到具体环节。

## 4. 持续 500 Hz 发送的反馈吞吐

另一组测试会持续发送，不等待上一帧的回复：

| 项目 | 左臂 | 右臂 |
| --- | --- | --- |
| 实际发送频率 | 约 499.98 Hz | 约 499.98 Hz |
| 发送数 | 2000 | 2000 |
| 收到反馈数 | 1802 | 1802 |
| 按首末内核接收时刻计算的反馈频率 | 约 447.33 Hz | 约 447.34 Hz |

反馈频率按 `(接收数 − 1) / (末帧时刻 − 首帧时刻)` 计算。两臂停止发送后，各收到 14 帧尾部反馈，最后一帧在停止后约 30.2～30.3 ms 到达。重复测试并继续接收 1 s，收帧总数仍然相同；主机网卡的错误和丢弃计数没有增加。

协议反馈不带请求序号，因此这组数据只能用于统计吞吐，无法逐请求配对计算延迟。198 帧的收发数量差还没有定位到具体环节。约 447 Hz 是本组设备、程序和负载下的测量结果。

## 5. 当前配置的依据与验证进度

3 ms 接收预算覆盖了本次约 2.4 ms 的内核往返和约 2.63 ms 的 SDK 交换中位数；4 ms 周期则为同步收发之外的工作留出时间。选择 250 Hz 的直接目的是获得完整反馈并便于调试，本轮没有做全频率扫描。

通信测试使用的是被动帧。使能保持、带载运动、长期跟踪和停止表现仍然需要实机验证。在更早一次真实 ROS 节点的 Disabled 预检中，两臂最近各 200 条反馈都有效，但左右臂分别跳过了 16 和 33 个控制时隙，最大循环间隔分别为 8.126 ms 和 8.087 ms。

历史记录中还包括 250 Hz 下的内存模拟运动、受控退出测试通过，以及旧净空模式中三项回归因 `collision validation time budget exceeded` 失败。后续代码先删除了强制几何路径检查及其 0.5 ms 预算，再把碰撞对象构建和距离查询整体移出控制内核。需要几何碰撞检测时，请在上层接入规划器；控制器只保留关节运动、制动和力矩约束。上述通信数据仍然对应原来的测量版本。

从 2 ms 改成 4 ms 后，主机参考和力矩的更新间隔也随之改变，但关节速度、加速度限制保持原值。普通位置模式会同时下发参考 q/dq 和 MCU Kp/Kd，阻抗模式的主臂 MCU Kp/Kd 为零；两种模式都需要在实际闭环中评价周期变化的影响。

## 6. 调高频率时的检查顺序

1. 记录主机、网卡和固件版本，测量完整交换耗时的分布、尾部延迟和反馈吞吐。逐请求延迟要使用明确配对的数据。
2. 确定同步或流水线的收发策略。当前同步实现要求接收预算小于周期，2 ms 周期配 3 ms 预算会在启动时报错。改变收发策略时，也要同时检查反馈时龄、积压处理和停止行为。
3. 在双臂、ROS 和 RViz 正常负载下，观察 `exchange_time`、`max_exchange_time`、`loop_period`、`max_loop_period`、`missed_control_slots`、`feedback_age`、`feedback_valid` 和 `overruns`。
4. 分阶段验证保持、运动跟踪和受控停止，用实际误差和停止表现来决定频率。
