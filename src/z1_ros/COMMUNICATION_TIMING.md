# 当前采用 250 Hz 控制周期、3 ms 接收预算的原因

记录日期：2026-10-27。本文的参数约束已随控制约束审核更新，历史实测数据保持原样。适用于本项目当前主机、两臂 MCU、网卡和 SDK 收发实现。

当前选择 **4 ms 控制周期（250 Hz）和 3 ms UDP 接收预算**，依据是：当前 SDK 的被动交换耗时中位数约 2.63 ms，原来的 1 ms 接收窗口经常无法取得新反馈；4 ms／3 ms 配置在多轮被动通信测试中完整收发，并为控制计算留出时间。这是已经过通信验证的调试配置，尚未完成真机运动闭环验收，也不是对机械臂硬件频率上限的判断。

## 1. 两个参数分别控制什么

| 项目 | 原配置 | 当前配置 | 配置位置 |
| --- | --- | --- | --- |
| 主机控制周期 `period` | `0.002 s`，500 Hz | `0.004 s`，250 Hz | [control.yaml](z1_bringup/config/control.yaml) |
| 左右臂 UDP 接收预算 `receive_budget_us` | `1000 μs` | `3000 μs` | [communication.yaml](z1_bringup/config/communication.yaml) |

`period` 决定每个上位机控制线程的目标执行节拍。它没有修改 MCU 或电机内部控制频率；两臂各有一个独立控制线程，也不是两臂分摊 250 Hz。

`receive_budget_us` 是接收代码一次等待回复的时间上限。报文到达即可继续执行，不会固定等待满 3 ms。该时间上限也包含操作系统唤醒误差，不能当作线程绝对不超时的保证。

以下参数属于不同环节：

- `publish_rate: 100.0` 是 ROS 状态发布频率，不是电机控制频率。
- `feedback_timeout: 0.08` 是反馈有效期判定，不是每次阻塞等待 80 ms。
- 标定工具独立使用 10 ms 采样间隔、5 ms 接收预算，不受这里的 4 ms／3 ms 运行节拍直接控制。

## 2. 为什么需要一起调整周期和接收预算

[runtime.cpp](z1_control/src/runtime.cpp) 在同一个控制线程内按顺序执行：

```text
发送上一轮输出 → 接收 MCU 反馈 → 计算下一轮输出 → 等待下一个控制时隙
```

因此，收发和控制计算共同占用一个周期。接收预算增大到 3 ms 后，仍使用 2 ms 周期无法为这条同步执行路径提供完整的时间预算。

[ros_node.cpp](z1_control/src/ros_node.cpp) 检查以下配置关系：

```text
receive_budget_us × 10⁻⁶ < period
```

当前为：

```text
3 ms < 4 ms
```

删除几何强制拦截后，原有 0.5 ms 几何验证预算也已删除。当前接收预算之外约有 1 ms 用于控制计算和调度；它不是实测保证。

线程按绝对时间等待下一个时隙，**不是每次收发结束后再额外睡眠 4 ms**。错过时隙时会跳过已过期时隙并计数，不会连续补发旧周期。因此，250 Hz 是目标频率，实际节拍还要检查 `missed_control_slots`、`loop_period` 等状态。

## 3. 直接支持这次选择的实测结果

通信测试仅发送发现请求和 140 字节全零被动帧，没有使能、运动目标或标定请求。原始 UDP 测速程序不经过 ROS、运动学、动力学或 SDK 解码；另用项目现有 SDK 收发路径进行对照。

两臂各使用一块 `ax88179_178a` USB 网卡，以太网链路均为 100 Mbps 全双工，USB 侧速率为 5000 Mbps。测试时网卡运行时电源状态为 active。MCU／电机固件版本未确认，因此本记录不声称适用于其他固件版本。

### 3.1 现有 SDK：原配置经常错过接收窗口

以下是同日复测，每种条件、每臂各交换 500 次：

| 机械臂 | 周期／接收预算 | 取得新有效反馈 | 最长连续未取得新反馈 | 交换耗时中位数／最大值 |
| --- | --- | --- | --- | --- |
| 左 | 2 ms／1 ms | 268／500 | 5 次 | 此组包含接收超时，不用于估计完整回复耗时 |
| 右 | 2 ms／1 ms | 269／500 | 5 次 | 此组包含接收超时，不用于估计完整回复耗时 |
| 左 | 4 ms／3 ms | 500／500 | 0 次 | 2.632／2.829 ms |
| 右 | 4 ms／3 ms | 500／500 | 0 次 | 2.639／2.728 ms |

更早一次同样的测试中，2 ms／1 ms 条件下左、右臂分别取得 263／500 和 270／500 次新反馈，4 ms／3 ms 条件下均为 500／500。说明现象可复现，单次计数会波动。

这里的计数是“本轮同步接收窗口是否取得新有效反馈”，**不能把未取得反馈的次数直接解释为以太网丢包**。回复可能晚于窗口到达；当前传输层还会在下一次请求前清理旧队列，避免把积压报文重新标记为新反馈。

这组对照同时修改了周期和接收预算，不能单独证明降低频率是改善的全部原因。

### 3.2 内核时间戳：主要等待位于主机网络收发路径之间

使用 Linux `SO_TIMESTAMPING` 软件发送、接收时间戳，先经回环模拟器验证。逐次请求测试只保留一个待回复请求，以减少旧反馈错配。

下表是单臂 250 Hz、每臂 1000 次的结果；单位 ms，除 P99 外均为中位数：

| 测量环节 | 左臂 | 右臂 |
| --- | --- | --- |
| 应用发送调用前 → 内核发送时间戳 | 0.0301 | 0.0208 |
| 内核发送 → 内核接收 | 2.4351 | 2.4328 |
| 内核接收 → 应用读到报文 | 0.0693 | 0.1152 |
| 应用一次完整交换 | 2.5353 | 2.5696 |
| 内核发送 → 接收的 P99 | 2.4522 | 2.4484 |
| 收到／发送 | 1000／1000 | 1000／1000 |

各列独立取分位数，不能要求中位数相加严格等于总耗时中位数。相同原始 UDP 程序在 100 Hz 下测得两臂内核往返中位数也约为 2.434 ms。

两臂同时以 250 Hz 运行时，各自 2000／2000 次收发完成，测试程序没有跳过发送时隙；内核往返中位数左臂 2.4334 ms、右臂 2.3436 ms。因此，约 2.4 ms 是实测量级，不能视为设备恒定的精确延迟。

同链路、140 字节 ICMP payload 的 ping 对照，每臂 20 次均收到回复，平均往返左臂 0.237 ms、右臂 0.265 ms。

据此可以优先排查机械臂 UDP 业务处理、固件任务节拍及内部电机通信；目前仍不能把全部约 2.4 ms 归因到 MCU。软件时间戳之间包含驱动、USB 网卡、链路及设备处理，ping 与控制 UDP 的处理路径也不同。

### 3.3 持续发送 500 Hz：未取得同等反馈吞吐

另以持续收发方式测试，不要求每轮必须等到回复后才发送下一帧：

| 项目 | 左臂 | 右臂 |
| --- | --- | --- |
| 主机实际发送频率 | 约 499.98 Hz | 约 499.98 Hz |
| 发送数 | 2000 | 2000 |
| 收到反馈数 | 1802 | 1802 |
| 按首末内核接收时刻计算的反馈频率 | 约 447.33 Hz | 约 447.34 Hz |

重复测试并在停止发送后继续接收 1 秒，收帧数量仍相同。两臂停止发送后均还有 14 帧尾部反馈，最后一帧约在停止发送后 30.2～30.3 ms 到达。

协议反馈没有请求序号，因此不能按收发顺序强行配对并计算这一组的逐请求延迟。198 帧数量差也不能直接定位为某个网络环节丢包。测试期间主机网卡错误及丢弃计数没有增加。

这说明当前组合尚未验证出 500 Hz 的完整反馈吞吐，不能把约 447 Hz 当作所有 Z1 固件或硬件的上限。

## 4. 为什么具体选 250 Hz 和 3 ms

- **3 ms 接收预算**覆盖本次实测约 2.4 ms 的内核往返和约 2.63 ms 的 SDK 完整交换。原来的 1 ms 窗口明显偏短，3 ms 仍需结合尾部延迟和超时计数观察。
- **4 ms 周期**可容纳这条同步收发路径及控制计算，并且已有单臂和双臂被动测试数据支持。
- 本轮没有完成所有候选周期的比较，也没有证明 250 Hz 是最优频率。当前选择优先保证调试时反馈完整、节拍可观察，而不是宣称其他频率不可行。

主臂反馈控制和动力学补偿由上位机执行，因此从 500 Hz 改为 250 Hz 会改变闭环更新间隔，可能影响动态响应、轨迹跟踪和抗扰动能力。关节速度、加速度限制不会因此自动减半；它也不等于 RViz 刷新率变化。

## 5. 已验证与未验证的范围

已验证本机当前设备组合下的短时被动收发、内核软件时间戳、SDK 接收窗口对照及双臂同时通信。另有 250 Hz、净空保护关闭条件下的内存模拟运动和受控退出测试通过；这不等同于真机运动测试。

更早的真实 ROS 控制节点 Disabled 预检中，两臂最近各 200 条状态反馈均有效，但存在少量跳过控制时隙，最大循环间隔约 8 ms。因此，尚不能宣称完整控制器严格稳定运行于 250 Hz。使能保持、带载运动、连续运行的跟踪误差和停止表现仍需实际验证。

历史净空开启模式曾有三项离线回归因 `collision validation time budget exceeded` 失败。当前已删除强制几何路径检查及其 0.5 ms 预算，该失败路径不再存在；这属于控制约束删减，并不表示通信节拍能保证几何计算实时性。J4 标定参考值与通信节拍选择独立。

## 6. 后续考虑恢复 500 Hz 时应验证什么

1. 在相同设备和明确记录的主机配置下，重新记录发送、内核接收、应用读取时刻，确认完整延迟分布、尾部和反馈吞吐；避免将队列中的旧反馈当作新请求的回复。
2. 明确收发策略是否仍为当前同步路径。2 ms 周期不能直接搭配 3 ms 接收预算；若采用异步或流水线收发，需要验证反馈时龄、积压处理和停止行为。
3. 在双臂实际运行及正常 ROS/RViz 负载下观察 `exchange_time`、`max_exchange_time`、`loop_period`、`max_loop_period`、`missed_control_slots`、`feedback_age`、`feedback_valid` 和 `overruns`。计算超时与错过控制时隙是不同指标，应一起检查。
4. 分阶段验证实际保持、运动跟踪和受控停止，确认周期变化对闭环控制的影响。不能仅以“进程能启动”或一次 ping 很快作为恢复依据。
